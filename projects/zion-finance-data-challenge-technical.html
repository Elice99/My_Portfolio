The cost of failed transactions: how it was built

A reproducible Python pipeline, a 15-sheet Excel workbook, eight native charts, six report figures and a 64-check QA suite. This page covers the data grain, cleaning rules, metric definitions, validation and the architecture.

The solution

The original ZT_Finance_Challenge.xlsx was a pre-formatted skeleton with uncalculated formulas that displayed zeros. I left it untouched. The new workbook stores static computed values, so every number is correct on open in any spreadsheet engine.

I built a deterministic pipeline in five Python scripts plus one optional PowerShell export. Raw CSVs feed a preparation step, the prepared tables feed analysis, analysis writes tables and a summary, and the workbook and charts are generated from those outputs. A QA script recomputes the headline numbers and inspects the workbook.

The transaction rows are aggregates. One row can represent many payment attempts, so total attempts are the sum of total_count, not a row count. This distinction is the foundation of every rate in the analysis.

Currency

All monetary values are converted to USD. Fee amounts are already USD in the extract.

Period

The month label is parsed to the first day of the month. No daily or intra-month claim is possible.

Sector

A controlled mapping cleans free-text sectors. Blank sectors remain 'Unknown' rather than being dropped.

Preparation rules

  1. Parse the monthConvert the period label to a date at month start so monthly ordering is stable.
  2. Join customersAttach country, sector, customer status and sign-up date by customer_id.
  3. Clean sectorMap free-text sector values into a controlled set and keep blanks as Unknown.
  4. Derive failure flagsis_failed is 1 when status is failed. FailedCount and FailedRev_USD are derived from it.
  5. Convert currencyJoin a month-average daily FX rate by currency and month. Rows without a rate keep a missing USD value and are excluded from monetary sums.
  6. Freeze the grainWrite prepared tables once and build every analysis from them. Source files are never overwritten.

222 transaction rows have no matching month-average FX rate. I did not impute them. Count-based metrics use all rows; money-based metrics use only rows with a valid USD value. The exclusion is disclosed in the workbook and the data quality report.

Metric definitions

I kept the operational and financial lenses separate instead of forcing one headline rate.

Headline KPIs

scripts/analyse.py

This function is the core of the analysis. Attempts and fee revenue are summed from the prepared grain. The two failure rates are deliberately separate.

Headline KPIsPYTHON
def kpis(d: pd.DataFrame) -> dict:
    att = float(d["total_count"].sum())
    fatt = float(d["FailedCount"].sum())
    rev = float(d["Rev_USD"].sum())
    frev = float(d["FailedRev_USD"].sum())
    succ_att = att - fatt
    return {
        "attempts": att,
        "failed_attempts": fatt,
        "count_fail_rate": fatt / att if att else np.nan,
        "revenue_usd": rev,
        "failed_revenue_usd": frev,
        "revenue_fail_rate": frev / rev if rev else np.nan,
        "avg_fee_failed_att": frev / fatt if fatt else np.nan,
        "avg_fee_success_att": (rev - frev) / succ_att if succ_att else np.nan,
    }

Review note. Count failure rate answers how often payments fail. Revenue failure rate answers where the fee money sits. Both are reported everywhere.

Recovery

scenario formula

Recovery is a counterfactual. It assumes a segment can move from its current revenue failure rate to an explicit target.

RecoveryPYTHON
current = df["FailedRev_USD"].sum() / df["Rev_USD"].sum()
recovery = max(0.0, current - target) * df["Rev_USD"].sum()

Review note. Targets are assumptions, not forecasts. The mobilemoney floor of 77.3 percent is the best observed floor in the extract. The 85 percent card target is a staged improvement assumption.

FX method and missing rates

Each transaction row is a monthly aggregate. I use the average of the available daily rates for that currency in that month. This matches the grain of the transaction data and avoids pretending that a single day's rate applies to a whole month.

ChoiceRuleEffect
DEF-1Month-average daily rate by currencyOne consistent USD value for each monthly row
Missing ratesNo imputation222 rows excluded from monetary sums only
Fee revenueAlready USD in the extractNo conversion applied to fee columns

Reproduce it

Full pipelineBASH
python scripts/prepare_data.py
python scripts/analyse.py
python scripts/make_charts.py
python scripts/build_workbook.py
python scripts/qa_check.py

# Optional, Windows and Microsoft Excel only:
powershell -ExecutionPolicy Bypass -File scripts/export_workbook_pdf.ps1

No randomness, no external calls and no manual workbook edits. Re-running reproduces the same values.

Determinism

No random seed is used because no step is random. Only timestamps in prepare_manifest.json change.

Dependencies

Python 3.10+, pandas, numpy, openpyxl and matplotlib. The PDF export also needs Microsoft Excel.

Source safety

Raw CSVs and the original skeleton workbook are read-only inputs.

What I would change with better data

Failure reason

A reason code, provider identifier and retry flag would replace the persistence proxy with observed causes.

Daily grain

Daily rows would allow the brief's time-of-month question to be answered properly.

Fee lifecycle

Booked, reversed and refunded fee flags would tell us whether failed fee revenue is recoverable money or only a pricing counterfactual.

Automated gates

The QA script already runs 64 checks. In production I would wire it into CI so a failed reconciliation blocks publication.

The main judgement call was to report both failure lenses and to keep the recovery targets visibly assumed. It would have been easy to publish 90 percent as the failure rate and $2.84M as the prize. That would have been a cleaner story and a worse answer.
