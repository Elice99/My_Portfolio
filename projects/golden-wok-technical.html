The solution

The code on this page is the DAX and model logic from my project files, as I wrote it. Every number traces to my dashboard pages, my two project READMEs, and a direct profile of the CSVs I loaded.

I built this as a Power BI project: CSV source data prepared in Power Query, loaded into a star-schema model, and surfaced through a five-page report. The model separates transactional facts from descriptive dimensions so every page can slice delivery performance by kitchen, zone, rider, time and operating conditions. The five pages follow the operational chain I wanted management to walk: executive state, delivery friction and SLA, profitability, customer experience, then corridor and network intelligence.

ComponentWhat I built it fromRole
fact_orders5,000 rows, 15 fieldsOne row per delivery: kitchen, zone, rider, time slot, promise and actual times, distance, traffic score, costs, profit, rating
dim_kitchen4 rowsKitchen name, LGA, hourly capacity, opening date, active status
dim_delivery_zone20 rowsZone name, LGA, tier, traffic index, population density, baseline delivery time, restricted-zone flag
dim_rider60 rowsAssigned kitchen, vehicle type, experience, average speed, rating, active status
dim_time_slot48 rows, plus a cleaned reference tableOriginal slots, then my derived hour, day of week, rush-hour flag and meal period
dim_dateCalculated in DAXTime intelligence for the trends
The report5 pages in Power BI DesktopExecutive, SLA control, profitability, customer experience, network intelligence

A direct profile of the orders shows the model touches 15 of the 20 zones and 24 of the 60 riders; the rest exist in the dimensions without orders in this dataset. I mention that so the dimension row counts and the dashboard counts do not look contradictory.

The data model

The relationships are the classic star: the fact table filters its dimensions, one rider dimension is conformed to kitchens, and the date table carries the trends.

Model relationshipsTEXT
fact_orders[kitchen_id]        -> dim_kitchen[kitchen_id]
fact_orders[zone_id]           -> dim_delivery_zone[zone_id]
fact_orders[rider_id]          -> dim_rider[rider_id]
fact_orders[time_slot_id]      -> dim_time_slot[time_slot_id]
dim_rider[assigned_kitchen_id] -> dim_kitchen[kitchen_id]
fact_orders[order_date]        -> dim_date[Date]

One modelling decision worth calling out: the supplied time-slot table carried the raw slot information, but I derived a cleaned reference table for the analytical attributes I actually needed, hour of day, day of week, rush-hour classification and meal period. Building those once in the dimension kept the DAX simpler and the slicers consistent across pages.

The measures and the decisions inside them

The KPI layer is deliberately plain. I wanted every headline number to be auditable from its definition.

Executive KPIsDAX
Total Orders =
DISTINCTCOUNT ( fact_orders[order_id] )

Total Revenue =
SUM ( fact_orders[order_value_ngn] )

Total Profit =
SUM ( fact_orders[order_profit_ngn] )

Profit Margin =
DIVIDE ( [Total Profit], [Total Revenue] )

The SLA layer

SLA measuresDAX
SLA Breaches =
CALCULATE (
    [Total Orders],
    fact_orders[actual_delivery_min] > fact_orders[promised_delivery_min]
)

SLA Breach Rate =
DIVIDE ( [SLA Breaches], [Total Orders] )

Avg Promise Gap =
AVERAGEX (
    fact_orders,
    fact_orders[actual_delivery_min]
        - fact_orders[promised_delivery_min]
)

Severe Delay Orders =
CALCULATE (
    [Total Orders],
    FILTER (
        fact_orders,
        fact_orders[actual_delivery_min]
            > fact_orders[promised_delivery_min] + 60
    )
)

The severity banding is where the report earns its diagnostic value. Rather than treating every breach the same, I classify each order by how far past the promise it landed, which is what exposed the bimodal early-versus-severe split on page two.

SLA severityDAX
SLA Severity =
VAR Gap =
    fact_orders[actual_delivery_min]
        - fact_orders[promised_delivery_min]
RETURN
    SWITCH (
        TRUE (),
        Gap < 0, "Early",
        Gap = 0, "On Time",
        Gap <= 15, "Late 1-15 min",
        Gap <= 30, "Late 16-30 min",
        Gap <= 60, "Late 31-60 min",
        "Severe >60 min"
    )

The banding features

Distance and traffic bandsDAX
Distance Band =
VAR Distance = fact_orders[delivery_distance_km]
RETURN
    SWITCH (
        TRUE (),
        Distance <= 2, "0-2 km",
        Distance <= 4, "2-4 km",
        Distance <= 6, "4-6 km",
        Distance <= 8, "6-8 km",
        Distance <= 10, "8-10 km",
        "10+ km"
    )

Traffic Friction Band =
VAR Traffic = fact_orders[traffic_friction_score]
RETURN
    SWITCH (
        TRUE (),
        Traffic < 3, "Low",
        Traffic < 5, "Moderate",
        Traffic < 7, "High",
        "Very High"
    )

Distance bands drive the cost story

The 6 to 8 km band carries ₦5.44K per kilometre against ₦1.2K at 4 to 6 km. One band boundary carries most of the insight, which is why I built the band as a column the whole report shares.

Traffic bands are mine, not the data's

I defined the Low to Very High thresholds for display. I say so on the page, because presenting an analytical bucket as an external standard would be dishonest.

Severe means one hour late

The 60-minute severe threshold matches the severity bands, so the severe-delay card and the severity distribution reconcile by construction.

Sort columns keep bands honest

The traffic band has a numeric sort column so Low, Moderate, High and Very High never alphabetise.

The customer-experience layer carries a small detail I am fond of: the star display and the numeric label are computed from the same rounded value, so the stars and the text can never disagree.

Customer experienceDAX
Low Rating Orders =
CALCULATE (
    [Total Orders],
    fact_orders[customer_rating] < 2.5
)

Customer Rating Stars =
VAR Rating =
    ROUND ( [Avg Customer Rating], 1 )
VAR FullStars =
    INT ( Rating )
VAR EmptyStars =
    5 - FullStars
RETURN
    REPT ( "★", FullStars )
        & REPT ( "☆", EmptyStars )

The economics layer

Cost and profitabilityDAX
Delivery Cost per KM =
DIVIDE (
    SUM ( fact_orders[delivery_cost_ngn] ),
    SUM ( fact_orders[delivery_distance_km] )
)

Delivery Cost % of Order Value =
DIVIDE (
    SUM ( fact_orders[delivery_cost_ngn] ),
    SUM ( fact_orders[order_value_ngn] )
)

Loss-Making Orders =
CALCULATE (
    [Total Orders],
    fact_orders[order_profit_ngn] < 0
)

The dynamic pressure analysis

Three outputs on the network page compute themselves from the current filter context, and each one has a sample-size or definition decision baked in.

The highest-pressure corridor ranks kitchen-to-zone pairings by SLA breach rate, but only past a minimum-order threshold. Without it, a five-order corridor with a 100% breach rate would top the list. With it, the callout points at Ikeja GRA to Alimosho, 64.52% on 62 orders, which is a finding someone can act on.

Corridor ranking logicTEXT
Kitchen x Zone
      |
Calculate Orders
      |
Calculate SLA Breach Rate
      |
Keep corridors with sufficient volume
      |
Rank by SLA pressure
      |
Return highest-pressure corridor

The highest distance exposure works the same way: distance bands ranked by breach rate past a volume threshold, currently 6 to 8 km at 53.28% on 259 orders.

The capacity comparison is the one I had to define carefully. The kitchen capacity field is stated as orders per hour, so dividing total daily orders by it would be meaningless. I aggregate demand to the operating hour first, take the peak observed hour, and compare that with capacity, which puts highest utilisation at 6.67% in this dataset.

Capacity utilisation logicTEXT
Daily transaction data
        |
Date + operating hour
        |
Hourly order volume
        |
Peak observed hourly demand
        |
Compare with kitchen capacity
        |
Capacity utilisation

Data quality calls I made

I treated data quality as part of the analysis rather than something to clean quietly. Three calls define what the report can and cannot claim.

FieldWhat I foundWhat I did
food_temp_on_arrival_cValues I could not validate as plausibleExcluded it from the customer-experience analysis entirely, and said so on the page rather than transforming it silently
actual_delivery_minValues stretching to operationally implausible durations (P90 reads 899 minutes)Reported it as observed, and labelled P90 and the averages as dataset observations, not real-world delivery benchmarks
traffic_friction_scoreA generated score with no external standardBanded it for display and labelled the bands as analytical categories

The generated validation report that shipped with the challenge data passed 10 of 10 checks, which covers structural integrity, not plausibility. The plausibility judgement was mine, and the food-temperature exclusion is the honest example: the field exists, the values do not earn trust, so the field does not appear in my conclusions.

One reading note I keep making: the dashboard's zone-tier breach rates sit between 48.87% and 50.28%, so tier alone explains almost nothing. That is why my findings lead with distance bands and corridors rather than zone labels.

My decisions and trade-offs

Decision I madeWhyTrade-off I accepted
Excluded food temperature rather than transform itThe values could not be validated, and a silent transform would invent signalThe customer page loses a field the brief hypothesised about
Minimum-volume thresholds on corridor and distance rankingsAn extreme rate on a tiny sample would misdirect managementA genuinely failing low-volume corridor waits longer for attention
Hourly capacity comparison instead of daily totalsCapacity is defined per hour; daily division would be meaninglessMore complex measure logic than a simple ratio
Analytical traffic bands with visible labellingDisplay buckets make the friction matrix readableA reader could mistake my thresholds for official standards, so I label them
Reported order profit as suppliedThe profit field is the challenge's own definitionMy profitability conclusions inherit whatever assumptions the generator made
Kept delivery-time outliers visible with a caveatTrimming them would flatter the averages and hide the severe-delay problemP90 and averages look alarming until you read the framing
Built severity and distance bands as model columnsEvery page, card and matrix bands the same wayChanging a boundary means touching the model, not just a visual

Publication and next steps

  1. Publish the repositoryThe READMEs, the PBIX and the dataset profile are ready; the repo is the next deliverable so everything here is reproducible.
  2. Test the brief's hypotheses directlyThe brief proposes rain effects, rush-hour-to-outer-zone failures and the Lekki corridor question; my model has the slices, the segment-level measures are the next build.
  3. Add the loss-making order cutThe Loss-Making Orders measure exists; surfacing its rate by zone would quantify exactly which corridors price below their cost.
  4. Re-run the corridor ranking on any refreshThe dynamic callouts are filter-context driven, so a new dataset recomputes them; the thresholds are the only constants to review.
  5. Benchmark against real delivery timesBefore reusing the framework on live data, promise and actual distributions need real-world calibration.

What this project shows

This is my attempt at the difference between a scorecard and a diagnosis. The same 5,000 orders could have produced five pages of totals; instead the report connects operating conditions to friction, friction to SLA, SLA to money, and both to the customer, and it lands on named corridors rather than vague pressure.

The habits I would carry forward: put sample-size discipline inside the ranking logic so the insight survives without me in the room, label analytical bands as analytical, and when a field does not earn trust, exclude it out loud.
