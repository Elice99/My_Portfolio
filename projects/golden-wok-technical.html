Golden Wok Delivery Intelligence: how I built it

The model behind the report: the Power BI project structure, the star schema and its relationships, the Power Query preparation, the DAX measures with the decisions inside them, the dynamic pressure analysis, and the data-quality calls I made on the way.

The solution

The DAX and Power Query on this page come from my model definition files, as I wrote them. Every number traces to my dashboard pages, my two project READMEs, and a direct profile of the shipped CSV files.

I built this as a Power BI project: CSV source data prepared in Power Query, loaded into a star-schema model, and surfaced through a five-page report. My project folder is a PBIP workspace, with the semantic model and report definition in separate folders and the PBIX as the shipped artifact. Inside the model I organized measures into five display folders that mirror the report's chain, Core KPIs, Delivery & SLA, Profitability, Operations, Customer Experience, plus an Analysis folder for the dynamic callouts, so anyone opening the model sees the same structure the report walks.

ComponentWhat I built it fromRole
fact_orders5,000 rows, 15 fieldsOne row per delivery: kitchen, zone, rider, time slot, promise and actual times, distance, traffic score, costs, profit, rating
dim_kitchen4 rowsKitchen name, LGA, hourly capacity, opening date, active status
dim_delivery_zone20 rowsZone name, LGA, tier, traffic index, population density, baseline delivery time, restricted-zone flag
dim_rider60 rowsAssigned kitchen, vehicle type, experience, average speed, rating, active status
dim_time_slot48 rows, sourceOriginal slot labels with hour, day, rush flag, meal period and weather
dim_time_slot_cleanMy Power Query derivationSlot start and end times, numeric hour, my own rush-hour windows, cleaned meal periods, time bands and sort keys

A direct profile of the orders shows the model touches 15 of the 20 zones and 24 of the 60 riders; the rest exist in the dimensions without orders in this dataset. I mention that so the dimension row counts and the dashboard counts do not look contradictory.

The Power Query preparation

The source tables needed two kinds of cleaning, and both happened in Power Query rather than in DAX, because preparation belongs in the loading layer.

First, the kitchen names. The CSV ships them as "Golden Wok Yaba Central" and friends, which is redundant next to a report that already says Golden Wok everywhere, so I strip the prefix on load. What is left keeps a leading space, and my DAX measures match that exactly. It looks odd in the code and it is deliberate.

Kitchen name cleanup (dim_kitchen query)PYTHON
#"Replaced Value" = Table.ReplaceValue(
    #"Changed column type", "Golden Wok", "",
    Replacer.ReplaceText, {"kitchen_name"})

Second, and more involved: the time-slot table. The raw slot_label reads like "07:30-08:00", which no visual can sort or slice properly. I derived a clean reference table that parses the label into start and end times, pulls the numeric hour, and then rebuilds the analytical attributes I actually needed. The rush-hour definition matters most: I hard-coded the brief's own windows, 07:00 to 09:00 and 16:30 to 19:30, so my rush-hour analysis tests exactly what the brief claimed.

Rush-hour windows, straight from the brief (dim_time_slot_clean query)PYTHON
#"Added Custom3" = Table.AddColumn(PreviousStep, "is_rush_hour_clean",
    each if ([slot_start_time] >= #time(7,0,0) and [slot_start_time] < #time(9,0,0))
         or ([slot_start_time] >= #time(16,30,0) and [slot_start_time] < #time(19,30,0))
    then "Yes" else "No")

The same query derives cleaned meal periods (Breakfast 6 to 11, Lunch 11 to 15, Dinner 15 to 22, Late Night after), Morning/Afternoon/Evening/Night time bands, and a numeric sort key so every time visual sorts by actual time instead of alphabetically. Building these once in the dimension kept the DAX simple and the slicers consistent across all five pages.

The data model

The relationships are the classic star: the fact table filters its four dimensions, and the rider dimension is conformed to kitchens through its assigned-kitchen column, so kitchen analysis can see rider attributes without a second fact path.

Model relationshipsTEXT
fact_orders[kitchen_id]        -> dim_kitchen[kitchen_id]
fact_orders[zone_id]           -> dim_delivery_zone[zone_id]
fact_orders[rider_id]          -> dim_rider[rider_id]
fact_orders[time_slot_id]      -> dim_time_slot_clean[time_slot_id]
dim_rider[assigned_kitchen_id] -> dim_kitchen[kitchen_id]
fact_orders[order_date]        -> dim_date[Date]

Inside fact_orders I added the banding columns the whole report shares: an SLA severity column with a matching sort column, a distance band with its sort column, and month helpers for the trend visuals. I built them as model columns rather than measures on purpose, so every page, card and matrix bands the same way, and the sort columns keep Early through Severe and 0-2 km through 10+ km from ever alphabetising.

SLA severity and its sortPYTHON
column 'SLA Severity' =
    VAR Gap = fact_orders[actual_delivery_min]
              - fact_orders[promised_delivery_min]
    RETURN SWITCH ( TRUE (),
        Gap < 0,  "Early",
        Gap = 0,  "On Time",
        Gap <= 15, "Late 1-15 min",
        Gap <= 30, "Late 16-30 min",
        Gap <= 60, "Late 31-60 min",
        "Severe >60 min" )

column 'SLA Severity Sort' =
    SWITCH ( fact_orders[SLA Severity],
        "Early", 1, "On Time", 2, "Late 1-15 min", 3,
        "Late 16-30 min", 4, "Late 31-60 min", 5,
        "Severe >60 min", 6, 99 )
Distance band and its sortPYTHON
column 'Distance Band' =
    VAR Distance = fact_orders[delivery_distance_km]
    RETURN SWITCH ( TRUE (),
        Distance <= 2,  "0-2 km",
        Distance <= 4,  "2-4 km",
        Distance <= 6,  "4-6 km",
        Distance <= 8,  "6-8 km",
        Distance <= 10, "8-10 km",
        "10+ km" )

The measures and the decisions inside them

The KPI layer is deliberately plain. I wanted every headline number to be auditable from its definition.

Executive KPIs (Core KPIs table)DAX
Total Orders = DISTINCTCOUNT ( fact_orders[order_id] )

Total Revenue = SUM ( fact_orders[order_value_ngn] )

Total Profit = SUM ( fact_orders[order_profit_ngn] )

Profit Margin = DIVIDE ( [Total Profit], [Total Revenue] )

Avg Order Value = DIVIDE ( [Total Revenue], [Total Orders] )

P90 Actual Delivery =
PERCENTILEX.INC ( fact_orders,
    fact_orders[actual_delivery_min], 0.90 )

The trend layer uses month-over-month measures on the date intelligence, so the executive page can show orders, revenue and profit movement without me rebuilding anything on refresh.

Month-over-month patternDAX
Total Revenue MoM % =
VAR CurrentRev = [Total Revenue]
VAR PreviousRev =
    CALCULATE ( [Total Revenue],
        DATEADD ( fact_orders[order_date].[Date], -1, MONTH ) )
RETURN DIVIDE ( CurrentRev - PreviousRev, PreviousRev )

The SLA layer

SLA measures (Delivery & SLA table)DAX
SLA Breaches =
CALCULATE ( [Total Orders],
    fact_orders[actual_delivery_min]
        > fact_orders[promised_delivery_min] )

SLA Breach Rate = DIVIDE ( [SLA Breaches], [Total Orders] )

SLA Compliance rate = 1 - [SLA Breach Rate]

Avg Delivery Variance =
[Avg Actual Delivery] - [Avg Promised Delivery]

Severe Delay Orders =
CALCULATE ( [Total Orders],
    FILTER ( fact_orders,
        fact_orders[actual_delivery_min]
            > fact_orders[promised_delivery_min] + 60 ) )

One measure on this page I am particularly happy with writes its own sentence. The executive card does not show a naked number, it reads the variance, picks a direction word and an icon, and composes the takeaway. When the data refreshes, the sentence rewrites itself, which is the whole point of a dynamic report.

The self-writing delivery summaryDAX
Delivery Exec Summary =
VAR promise = [Avg Promised Delivery]
VAR actual  = [Avg Actual Delivery]
VAR varianc = [Avg Delivery Variance]
VAR stat = IF ( varianc >= 0, "ahead of", "behind" )
VAR icon = IF ( varianc >= 0, UNICHAR ( 9679 ), UNICHAR ( 9660 ) )
RETURN
    "We are delivering " & icon
        & FORMAT ( ABS ( varianc ), "#,0" )
        & " minutes " & stat & " promise." & UNICHAR ( 10 )
    & "Promise: " & FORMAT ( promise, "#,0" )
        & " min | Actual: " & FORMAT ( actual, "#,0" ) & " min"

The economics layer

Cost and profitabilityDAX
Delivery Cost per KM =
DIVIDE ( SUM ( fact_orders[delivery_cost_ngn] ),
         SUM ( fact_orders[delivery_distance_km] ) )

Delivery Cost % of Order Value =
DIVIDE ( SUM ( fact_orders[delivery_cost_ngn] ),
         SUM ( fact_orders[order_value_ngn] ) )

Loss-Making Orders =
CALCULATE ( [Total Orders],
    fact_orders[order_profit_ngn] < 0 )

Loss-Making Order Rate =
DIVIDE ( [Loss-Making Orders], [Total Orders] )

The Loss-Making Orders measure is the one that answers the brief's distance hypothesis directly. On this dataset it returns zero, which is itself the finding: there is no loss-making population to segment, so the corridor and promise stories take over.

The rider and customer layers

Rider benchmarking (Operations table)DAX
Rider Status =
VAR SLA = [SLA Breach Rate]
RETURN SWITCH ( TRUE (),
    SLA < 0.25, "STRONG",
    SLA < 0.50, "WATCH",
    "CONCERNING" )

Rider SLA Position =
VAR RiderSLA   = [SLA Breach Rate]
VAR NetworkSLA =
    CALCULATE ( [SLA Breach Rate], REMOVEFILTERS ( dim_rider ) )
RETURN SWITCH ( TRUE (),
    RiderSLA < NetworkSLA - 0.05, "BELOW NETWORK",
    RiderSLA > NetworkSLA + 0.05, "ABOVE NETWORK",
    "NEAR NETWORK" )

The rider page benchmarks each rider against the network, not against a fixed number, so the flag survives a data refresh. The customer layer carries the star display I am fond of: the stars and the numeric label compute from the same rounded value, so they can never disagree.

Customer experienceDAX
Low Rating Orders =
CALCULATE ( [Total Orders],
    fact_orders[customer_rating] < 2.5 )

Low Rating Rate =
DIVIDE ( [Low Rating Orders], [Total Orders] )

Customer Rating Stars =
VAR Rating = ROUND ( [Avg Customer Rating], 1 )
VAR FullStars = INT ( Rating )
VAR EmptyStars = 5 - FullStars
RETURN REPT ( "\u2605", FullStars ) & REPT ( "\u2606", EmptyStars )

The dynamic pressure analysis

Three outputs on the network page compute themselves from the current filter context, and each one has a sample-size or definition decision baked in. This is where the Analysis measure folder earns its keep.

The highest-pressure corridor ranks kitchen-to-zone pairings by SLA breach rate. I build the full cross join, compute orders and breach rate per pair, keep only corridors with at least 20 orders, then take the top row with a tie-break on volume. The 20-order minimum is the decision: without it, a five-order corridor with a 100% breach rate would top the list. With it, the callout points at Ikeja GRA to Alimosho, 64.52% on 62 orders, which is a finding someone can act on.

Highest Pressure Corridor (the real measure, condensed)DAX
VAR CorridorTable =
    ADDCOLUMNS (
        CROSSJOIN ( ALLSELECTED ( dim_kitchen[kitchen_id] ),
                    ALLSELECTED ( dim_delivery_zone[zone_id] ) ),
        "@Orders", CALCULATE ( [Total Orders] ),
        "@SLA",    CALCULATE ( [SLA Breach Rate] ) )

VAR ValidCorridors =
    FILTER ( CorridorTable,
        [@Orders] >= 20 && NOT ISBLANK ( [@SLA] ) )

VAR TopCorridor =
    TOPN ( 1, ValidCorridors, [@SLA], DESC, [@Orders], DESC )
-- then LOOKUPVALUE the kitchen and zone names and
-- return KitchenName & " -> " & ZoneName

The highest distance exposure reuses the same pattern over distance bands instead of corridors, same 20-order floor, currently pointing at the 6 to 8 km band at 53.28% on 259 orders. A companion measure writes the sentence into a card so the page explains itself.

The distance insight cardDAX
Distance Pressure Insight =
"Highest SLA pressure occurs in " & [Highest Risk Distance Band]
    & " at " & FORMAT ( [Highest Risk Distance SLA], "0.0%" )
    & " breach rate."

The capacity comparison is the one I had to define carefully. The kitchen capacity field is stated as orders per hour, so dividing total daily orders by it would be meaningless. I aggregate demand to the operating hour first with a SUMMARIZE over date and hour, take the peak observed hour, and compare it with capacity. That puts peak hourly demand at 3 orders and highest utilisation at 6.67% in this dataset, which is itself a finding: capacity is nowhere near the constraint.

Capacity utilisationDAX
Peak Hourly Orders =
MAXX (
    SUMMARIZE ( fact_orders,
        fact_orders[order_date].[Date],
        dim_time_slot_clean[hour],
        "@Hourly Orders", [Total Orders] ),
    [@Hourly Orders] )

Peak Capacity Utilization =
DIVIDE ( [Peak Hourly Orders],
         MAX ( dim_kitchen[kitchen_capacity_orders_hr] ) )

Data quality calls I made

I treated data quality as part of the analysis rather than something to clean quietly. Four calls define what the report can and cannot claim, and the first two are the ones I would highlight in a review.

What I foundWhat I did
The food-temperature field reads around 500°C with values up to 999.9. No food is an oven. It also fails the brief's own hypothesis: cold orders rate 3.04, warm ones 3.00.Excluded it from every conclusion, and said so on the page rather than transforming it silently.
The shipped data dictionary does not describe the shipped CSVs: it promises 25 to 45 minute deliveries and five weather values including Clear, while the file carries promises of 0 to 1,000 minutes and eight weather values with no Clear.Profiled the CSVs directly and worked from the actual data. The dictionary mismatch is documented in my README so nobody reproduces this from the dictionary alone.
Delivery times stretch to operationally implausible durations (P90 at 899 minutes, promises averaging 505).Reported as observed, and labelled P90 and the averages as dataset observations, not real-world delivery benchmarks.
The traffic friction score is a generated 0 to 10 number with no external standard.Banded it for display and labelled the bands as analytical categories in my README.

The generated validation report that shipped with the challenge data passed 10 of 10 checks, which covers structural integrity, not plausibility. The plausibility judgement was mine, and the food-temperature exclusion is the honest example: the field exists, the values do not earn trust, so the field does not appear in my conclusions.

My decisions and trade-offs

Profiled the CSVs instead of trusting the dictionaryThe dictionary and the data disagree on several fieldsAnyone reproducing from the dictionary alone will get different answers, so I documented the mismatch

Publication and next steps

  1. Publish the repositoryThe READMEs, the PBIX, the PBIP model definition and the dataset profile are ready; the repo is the next deliverable so everything here is reproducible.
  2. Surface the loss-making order cutThe measure exists; on this data it reads zero, which is worth showing as its own card so the brief's profit-cliff claim is answered on the page, not just in the docs.
  3. Add a weather-adjusted promise scenarioHeavy Rain adds 38 minutes; a measure-side scenario that extends promises under rain would quantify how much of the breach rate is weather-predictable.
  4. Re-run the corridor ranking on any refreshThe dynamic callouts are filter-context driven, so a new dataset recomputes them; the 20-order threshold is the only constant to review.
  5. Benchmark against real delivery timesBefore reusing the framework on live data, promise and actual distributions need real-world calibration.

What this project shows

This project is my attempt at the difference between agreeing with a brief and testing one. The brief handed me five confident claims; I built the model that could check all of them, found three of them false, and built the report around what the data actually supports: promise calibration, corridor pressure and a weather effect larger than the one the brief predicted.

The habits I would carry forward: put sample-size discipline inside the ranking logic so the insight survives without me in the room, write measures that explain themselves so the report stays current on refresh, profile the data instead of trusting its documentation, and when a field or a hypothesis does not earn trust, say so out loud.
