CRM Sales Analytics: what the model is worth

A cleaned SQL layer, a Power BI dashboard for what happened, and an XGBoost model behind a FastAPI service for what might happen next. This page covers what each layer does, what the model says about the 1,589 open deals, and where every number comes from in my own saved outputs.

The problem

The data is a public CRM practice dataset (a sales pipeline with accounts, products and sales teams). SPOTA, the company in the brief, is the fictional framing I wrote the project against. Nothing here measures a real company's revenue.

The brief describes a B2B company with the usual sales reporting problems: performance scattered across regions, products and agents; no shared view of the funnel; no way to know which open deals deserve attention; and coaching decisions made on gut feel.

I built three things that answer it in layers. A SQL Server database with two cleaning scripts, so every consumer reads the same corrected tables. A three-page Power BI dashboard with DAX measures for the descriptive questions: revenue, win rates, agent rankings, month over month movement. And the predictive layer: an XGBoost model trained on closed deals, wrapped in a FastAPI service, containerised with Docker, and run against all 1,589 open deals in the data.

The model answers one question per deal: given what similar agents, accounts, products and sectors have done before, is this open deal likely to be won?

The short answer

Three layers, one question per layer. A cleaned SQL layer gives everyone the same corrected tables, a Power BI dashboard answers what happened, and an XGBoost model behind a FastAPI service ranks the open pipeline for what might happen next. On the saved evaluation the tuned model separates winners from losers about 60% of the time (ROC-AUC 0.6085 on the held-out test set), and at the shipped threshold it catches 95% of the real winners while 64% of its win calls are right, so I position it as a ranking aid for working the top of the list, not a forecast. Every number on this page traces to one metrics file the training run wrote, and each one says where it comes from.

What I found

01

The model ranks deals, it does not predict them

How good is the model, really?

On the saved evaluation the tuned model reaches a ROC-AUC of 0.6085 on the held-out test set, with 62.8% accuracy. Naively calling every deal won would score 63.1% accuracy on the same set, so raw accuracy is not the story; the ranked win probabilities are.

The path is traceable in one metrics file: a slim-feature baseline cross-validated at 0.591, the search's best five-fold candidate at 0.612, the winner confirmed at 0.613 across three repeats of five folds, and one single evaluation on the untouched test set landing at 0.6085. The test set is scored exactly once, after selection is finished.

What it means. The useful output is a ranked list of open deals, not a predicted outcome. Ranking is exactly what a sales coach needs: work the top of the list first.

Conclusion

Quote ROC-AUC 0.6085 (tuned model, held-out test) and treat the model as a ranking aid.

02

The scoring run was a path test, not a pipeline read

What does the model say about the deals that are open right now?

The deployed API scored all 1,589 open deals, and every one came back predicted to win, with probabilities from 0.65 to 0.87. The repo documents the run as illustrative, for a good reason: the deals are from 2016 and 2017, so at serve time each one is computed as roughly nine years old, far outside anything the model saw in training, where closed deals averaged about 48 days of age.

Feeding a nine-year-old deal into a model trained on weeks-old deals can only produce extreme outputs. The run proves the serve path works end to end; it does not describe a live pipeline, because this dataset is closed history rather than a working CRM.

What it means. A scoring service is only as current as the data feeding it. On fresh deals with recent engage dates, the same path would produce usable scores. On this vintage it can only show that the plumbing works.

Conclusion

Re-run the scoring on fresh engage dates before reading anything into predicted win shares.

03

The threshold is a business decision, and the numbers move with it

What do the numbers mean at the threshold the API actually uses?

At the shipped 0.5 threshold, the test evaluation gives precision of 63.8% (of the deals called wins, 63.8% actually won) and recall of 94.8% (it caught nearly every real winner). Because 63.2% of closed deals were won anyway, calling everything a win would score 63.2% precision, so at this operating point the model's edge shows in the ranking, not in the flag.

The training run also tuned the threshold on out-of-fold training predictions and landed at 0.425, which pushes recall to 100% on the test set. The API ships 0.5 and reports both probabilities on every call, so a caller can apply any cutoff their use case needs.

What it means. A coaching tool that must not miss a likely winner wants the low threshold. A tool that acts on every flag wants a higher one and better precision. The shipped setup serves the first.

Conclusion

Publish the threshold next to every precision and recall number, and choose it per use case.

04

Most of the missing values were structural, not dirty

How much cleaning did the data actually need?

2,089 of the 8,800 rows have no close value and no close date. That is exactly the count of the open deals: 1,589 engaging plus 500 prospecting. Those blanks are the pipeline working as expected, not a quality problem.

The real catches were elsewhere. The sector field holds the spelling error 'technolgy' in 12 accounts, which the cleaning script's case normalization does not fix. 1,425 rows have no account at all. The subsidiary_of column was 82.4% blank and was dropped. There are no duplicate opportunity ids, so the SQL deduplication step is a safety net that found nothing to delete.

What it means. The cleaning script ends with an audit query that counts nulls per deal stage. That instinct, measure then decide, is what makes the structural nulls visible as a pattern instead of a panic.

Conclusion

Treat nulls as information. These ones reconciled exactly to the deal stages.

05

Won deal values span three orders of magnitude

What does the revenue data actually look like?

Won deals run from $38 to $30,288, averaging $2,361, for a total of $10.0M in closed revenue. A spread that wide means the average describes very few real deals, and a quarter's revenue can hinge on a handful of them.

It also explains two modelling choices. Tree-based learners tolerate skew that would distort a linear model, and company size enters as a log transform, so a 34,000-employee account does not dominate every split.

What it means. Any revenue conversation should start from the distribution, not the average. The dashboard keeps deal size next to its own month-over-month movement for exactly this reason.

Conclusion

Report the spread alongside the mean, and treat aggregate forecasts as ranges.

What I would do next

01

Use the ranking, not the label

High priority
Evidence
At the shipped threshold the model flags nearly every deal as a win; the ranked probabilities, not the label, are the usable output.
What to do
Work the scored list top down for coaching calls, and review the bottom of the list for pipeline hygiene, instead of treating WON or LOST as verdicts.
What I expect
Coach time goes where the model actually sees signal.
02

Label the open deals when they close, then re-measure

High priority
Evidence
The 1,589 scored deals have no outcomes yet, so production accuracy is unmeasured.
What to do
Join eventual outcomes back to the scored CSV and compute precision and recall on real future deals.
What I expect
Replaces the held-out test estimate with a measured production number.
03

Score on fresh deals, not the 2016-17 vintage

High priority
Evidence
Serve-time deal age is computed from the engage date, so stale deals land years outside the training range and the scoring run came back all-wins.
What to do
Bound-check engage_date at the API edge, and schedule scoring runs on current data.
What I expect
Predicted win shares become readable as pipeline health.
04

Raise the threshold if win flags drive automation

Medium priority
Evidence
Precision is 63.8% at the shipped 0.5, with recall at 94.8%.
What to do
If win flags feed automated actions, raise the cutoff and quote the precision and recall measured at the new point.
What I expect
Fewer false alarms for anything downstream that acts on the flag.
05

Validate category spelling on entry

Medium priority
Evidence
The sector value 'technolgy' survives in 12 accounts because the cleaning only normalises case.
What to do
Enforce a sector list in SQL or at data entry, and backfill the typo.
What I expect
Group-bys and dashboards stop splitting technology into two buckets.
06

Pick the cutoff per use case at the caller

Medium priority
Evidence
The OOF-tuned 0.425 threshold is stored in the artifact; the API ships 0.5 with both probabilities on every response.
What to do
Quote the metrics measured at whichever cutoff a use case applies, not just the shipped one.
What I expect
Metrics and behaviour stay aligned as new use cases grow.

What this can't tell you

The data is a public practice dataset, so no conclusion here describes a real company's pipeline or revenue.

The 1,589 scored deals have no outcomes yet, so there is no production accuracy number, only the held-out test evaluation. The scoring run itself is illustrative: stale engage dates push deal age far outside the training range.

A ROC-AUC of 0.6085 estimated from about 6,700 deals carries real uncertainty, and accuracy (62.8%) sits at the naive always-win baseline (63.1%); the value is in the ranking, not the flag.

This project does not produce a revenue forecast. The forecast-accuracy numbers in the business brief are targets, not measurements.

The Power BI dashboard and the model share the database but were evaluated separately; I did not re-run the report visuals for this write-up.
