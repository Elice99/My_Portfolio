The solution

Every metric on this page comes from re-running my own pipeline against the shipped CSV, plus the source files themselves. The final model is a logistic regression, not the XGBoost an earlier description of this project mentioned; the shipped repository contains only the logistic regression path.

The design principle I care about in this build is that preprocessing and model ship as one pickle. The DictVectorizer learned its vocabulary from training data; freezing them together is what stops the serving path from inventing its own idea of what a categorical value means.

Data preparation, as I ran it

  1. Normalise columnsAll column names lowercased and underscored, then every categorical value lowercased and space-stripped, so one-hot encoding produces stable feature names.
  2. Coerce and imputeTotalCharges arrives with 11 whitespace-only values; I coerced to numeric and filled with 0. That choice is documented in my README as a known limitation: zero implies no billing history, which bends predictions for exactly the brand-new customers the model most needs to rank.
  3. Encode the targetChurn converted from yes/no strings to 1/0 integers.
  4. Split before anything elseAn 80/20 train-test split with random_state 1 gives 5,634 training and 1,409 test rows. The test set is touched exactly once, at the end.

The feature set is 3 numerical columns (tenure, monthlycharges, totalcharges) and 16 categoricals covering demographics, services and account configuration. DictVectorizer one-hot encodes the categoricals and passes the numerics straight through, dense output.

The model and its validation

Logistic regression with C=1.0 and max_iter=5000. The iteration cap is not cosmetic: my notebook first ran with 1,000 and threw convergence warnings, so the production script raises it to 5,000, which my README records along with the honest note that feature scaling is the better fix.

Training and validationPYTHON
def train(df_train, y_train, C=1.0):
    dicts = df_train[categorical + numerical].to_dict(orient='records')
    dv = DictVectorizer(sparse=False)
    X_train = dv.fit_transform(dicts)
    model = LogisticRegression(C=C, max_iter=5000)
    model.fit(X_train, y_train)
    return dv, model

I report ROC-AUC rather than accuracy throughout, and the class balance is why: 74/26 means a model predicting nobody churns scores 74% accuracy while being useless. AUC measures whether the model ranks churners above non-churners, which is the property a ranked worklist needs. My README's 85.8% accuracy phrasing is this same AUC wearing the wrong name.

Serving: the part I would partially redo

The serving layer is FastAPI with a Pydantic schema, not the Flask my technical README describes; the code and the Swagger screenshot show FastAPI, and the README predates the rewrite. Swagger UI comes free with FastAPI, which is what my second screenshot shows.

The endpointPYTHON
class CustomerInput(BaseModel):
    tenure: int
    monthly_charges: float
    total_charges: float
    contract: str

@app.post("/predict")
def predict(customer: CustomerInput):
    X = dv.transform([customer.dict()])
    y_pred = model.predict_proba(X)[0, 1]
    return {"churn_probability": float(y_pred), "churn": y_pred >= 0.5}

Now the honest engineering note, and it is the most instructive thing on this page: the CustomerInput schema accepts 4 fields, but the model trained on 19. DictVectorizer treats missing keys as absent features, which encode as zeros, so the API runs without error and silently scores each customer as if they had no gender, no services, no payment method and no internet type.

That is not a crash, it is worse: it is a prediction that looks confident and is not the one the validated model would give. I built the 4-field schema to make the demo readable in Swagger, and the full-featured version is the first item on my redo list. Any production integration would need the 19-field contract with the same names the DictVectorizer was fitted on.

The threshold is a flat 0.5. That is the right default for a demo and the wrong default for a retention budget, where the cost of a wasted offer and the cost of a lost customer are not symmetric, and the threshold should be tuned to that trade-off.

One pickle, two objects

The vectorizer and model serialize together, so the serving path cannot desynchronise from the training path.

Validation before the final fit

Cross-validation runs on the training split only; the test set is scored once, after the final model is trained on the full training split.

Fixed random_state

Split and folds both seed at 1, so every number on these pages is reproducible bit-for-bit.

My decisions and trade-offs

If I took it further

  1. Fix the serving contractExpand CustomerInput to the full 19 features and add a contract test that scores a fixed customer record and compares against the offline model, so drift becomes loud instead of silent.
  2. Tune the threshold to the economicsParameterise offer cost and customer value, then choose the probability cutoff that maximises expected savings rather than a default 0.5.
  3. Fix the imputationFill the 11 blank TotalCharges from a tenure-based expectation, and re-validate whether the low-tenure scores improve.
  4. Benchmark tree modelsRun gradient boosting through the same CV harness as a benchmark, and keep logistic regression if the AUC gap does not buy its interpretability cost.
  5. Explain individual scoresAttach per-customer feature contributions (SHAP or coefficient inspection) to the ranked worklist, so an agent sees why a customer scored high before calling them.

What this project shows

The build is deliberately boring in the best way: a linear model, a frozen vectorizer, a single artifact, and a validation harness that any teammate can re-run in seconds. Boring is what makes a scoring process maintainable.

The habits this project gave me: report the metric that matches the decision the model feeds, validate before the final fit and touch the test set once, re-run your own claims against your own code before publishing them, and when a serving schema drifts from a training schema, treat it as a defect rather than a demo convenience.
